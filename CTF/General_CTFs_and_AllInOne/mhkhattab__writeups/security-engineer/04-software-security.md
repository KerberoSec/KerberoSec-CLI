> **Portfolio scope:** Detailed notes on API security, the secure software development lifecycle, SAST, DAST, vulnerability validation, DevSecOps, and application-security investigation. Examples are for authorized labs and defensive engineering.

## Module coverage

This module connected application architecture with the delivery pipeline. The topics included:

- OWASP API Security risks;
- secure software development lifecycle (SSDLC);
- static application security testing (SAST);
- dynamic application security testing (DAST);
- understanding how vulnerabilities become attack paths;

The key lesson is that security testing is most valuable when it changes how software is designed and delivered. A scanner at the end of a release cycle cannot compensate for missing authorization, unsafe trust boundaries, or an uncontrolled software supply chain.

## 1. Security requirements in the software lifecycle

A secure lifecycle introduces security work before code reaches production.

### Requirements phase

Security requirements should be derived from:

- data classification;
- user and administrator roles;
- threat models;
- regulatory and contractual obligations;
- availability and recovery requirements;
- abuse cases;
- third-party and supply-chain dependencies.

Examples of verifiable requirements:

- Every API operation must enforce authorization server-side.
- Sensitive values must not appear in application logs or client-visible errors.
- Administrative actions must generate immutable audit events.
- Passwords must be stored using an approved password KDF with unique salts.
- Build artifacts must be generated by the controlled pipeline and signed before release.
- Dependencies with known critical exploitable vulnerabilities must block release unless an approved exception exists.

### Design phase

Security design review should identify:

- trust boundaries;
- privileged components;
- sensitive data flows;
- external services and webhooks;
- deserialization and parsing operations;
- asynchronous queues and state transitions;
- failure modes;
- tenant and object boundaries;
- secrets and key-management requirements.

A common mistake is to focus only on input validation. Many serious application risks are authorization, business-logic, workflow, or supply-chain problems that require design changes.

### Implementation phase

Controls include:

- parameterized database queries;
- centralized authorization libraries;
- safe output encoding;
- secure secret retrieval;
- dependency pinning;
- memory-safe APIs where applicable;
- standardized error handling;
- code review for high-risk changes;
- unit and integration tests for negative security cases.

### Verification phase

Use complementary methods:

- SAST for source-level patterns;
- software composition analysis (SCA) for dependencies;
- secret scanning;
- infrastructure-as-code scanning;
- DAST for runtime behavior;
- API testing;
- manual code review;
- penetration testing;
- abuse-case and business-logic testing;
- configuration and deployment review.

### Operations phase

Production security includes:

- vulnerability disclosure and intake;
- patch and dependency maintenance;
- runtime monitoring;
- incident response;
- key and certificate rotation;
- secure decommissioning;
- feedback from incidents into design and tests.

## 2. API security methodology

APIs expose data and business functions directly. A useful assessment begins with an inventory.

### Build an API inventory

For each API, record:

- base URL and environment;
- version;
- owning team;
- authentication mechanism;
- exposed endpoints and methods;
- request and response schemas;
- data classification;
- rate and resource controls;
- external consumers;
- deprecation status;
- logging and alerting coverage.

Undocumented or obsolete endpoints are difficult to secure because they may not receive current controls or testing.

### Authentication versus authorization

Authentication answers “who is this?” Authorization answers “may this identity perform this action on this object?”

For an endpoint such as:

```http
GET /api/v1/accounts/7421/invoices/991
Authorization: Bearer <token>
```

The server must validate:

1. the token signature and expected algorithm;
2. issuer, audience, expiry, and relevant claims;
3. permission to call the function;
4. permission to access account `7421`;
5. permission to access invoice `991` within that account;
6. any workflow or state constraints.

Changing an identifier must never be sufficient to cross tenant or ownership boundaries.

### Object-level authorization testing

A controlled test methodology:

1. create or obtain two lab users with separate objects;
2. capture a valid request from user A;
3. replace only the object identifier with user B’s object;
4. compare status code, body, timing, and side effects;
5. test read, update, delete, and nested resources;
6. test alternate encodings and object references;
7. verify audit events for denied attempts.

A secure response should deny the operation without leaking unnecessary object details.

### Function-level authorization

Do not assume an endpoint is protected because the UI hides it. Test administrative or internal-looking functions directly:

```http
POST /api/v1/admin/users/123/disable
```

Authorization should be enforced at a centralized policy layer or consistently in every relevant handler. Front-end route guards are not security boundaries.

### Mass assignment

Frameworks may bind request JSON directly to internal objects. If the server accepts fields such as `role`, `isAdmin`, `accountId`, or `creditLimit` without an allow-list, a client may modify protected properties.

Safer patterns:

- use dedicated request DTOs;
- explicitly map permitted fields;
- enforce authorization for state changes;
- reject unknown fields for sensitive operations;
- test nested object updates.

### Resource and rate controls

Rate limiting must consider identity, IP, token, endpoint cost, and business operation. Expensive actions: password reset, export, search, report generation, file processing: may need separate quotas and concurrency limits.

A robust design uses:

- maximum request size;
- bounded pagination;
- timeouts;
- queue limits;
- cost-aware quotas;
- per-user and per-tenant controls;
- retry and backoff rules;
- monitoring for distributed abuse.

### SSRF and outbound trust

APIs that fetch URLs, validate webhooks, import files, or generate previews may make server-side requests. Controls include:

- allow-listing destinations where possible;
- parsing and canonicalizing URLs before policy checks;
- resolving DNS and validating the final IP range;
- blocking loopback, link-local, private, and cloud metadata destinations when not required;
- restricting redirects;
- using an egress proxy;
- network-level outbound policy;
- logging destination and result.

Application validation should be reinforced by network controls because URL parsing and redirect behavior are complex.

## 3. Source-to-sink analysis

A repeatable secure-code review traces untrusted data from source to sensitive sink.

### Sources

- query and path parameters;
- HTTP headers;
- cookies;
- JSON or XML bodies;
- uploaded files;
- database values originally supplied by users;
- messages from queues;
- webhook payloads;
- environment variables and configuration controlled by lower-trust actors.

### Transformations

- decoding and normalization;
- validation;
- type conversion;
- sanitization;
- authorization checks;
- template rendering;
- serialization and deserialization.

### Sinks

- SQL/NoSQL queries;
- operating-system commands;
- filesystem paths;
- template engines;
- LDAP or XPath queries;
- outbound HTTP clients;
- HTML/JavaScript output;
- deserializers;
- logging systems;
- dynamic code execution.

The review question is not simply “is the value sanitized?” It is “is the control appropriate for this exact sink and context?” SQL parameterization does not protect a shell command; HTML encoding does not validate an authorization decision.

### Example: command construction

Unsafe conceptual pattern:

```python
os.system("convert " + uploaded_name + " output.pdf")
```

Safer design:

- avoid shell invocation;
- use a library API or argument array;
- generate server-side filenames;
- enforce file type and size;
- sandbox the conversion process;
- restrict filesystem and network access;
- set time and resource limits.

Example using an argument list:

```python
subprocess.run(
    ["convert", safe_input_path, safe_output_path],
    check=True,
    timeout=20,
    shell=False,
)
```

This reduces shell interpretation but does not remove parser vulnerabilities or malicious-file risk, so sandboxing remains important.

## 4. SAST, SCA, and secret scanning

### SAST

SAST examines code or intermediate representations without executing the application. It is effective for patterns such as:

- unsafe APIs;
- injection data flows;
- insecure cryptographic use;
- hard-coded secrets;
- missing validation in known frameworks;
- dangerous deserialization;
- path manipulation;
- logging of sensitive values.

Limitations:

- false positives;
- incomplete framework understanding;
- difficulty with runtime configuration and complex authorization;
- inability to prove exploitability in every case.

Triage should inspect source, data flow, reachability, control context, and impact.

### SCA

SCA identifies third-party components and known vulnerabilities. High-quality use requires:

- accurate lockfiles and manifests;
- transitive dependency visibility;
- package provenance;
- version and fix availability;
- exploitability analysis;
- removal of unused packages;
- monitored exception handling.

A CVE in an included package may be unreachable, while a lower-severity issue in an exposed code path may be more urgent.

### Secret scanning

Secrets may exist in:

- source files;
- Git history;
- CI configuration;
- container layers;
- build logs;
- test fixtures;
- documentation;
- crash dumps.

Removing the current file is not sufficient if the secret remains in history. The secret must be revoked or rotated, exposure assessed, history handled appropriately, and preventive controls added.

## 5. DAST and manual runtime testing

DAST tests a running application from the outside. It is useful for confirming:

- exposed endpoints;
- runtime headers and cookies;
- injection behavior;
- reflected and stored output;
- server error handling;
- authentication workflows;
- deployed configuration;
- TLS behavior;
- differences between environments.

### Baseline-first testing

Before changing requests:

1. capture a normal request;
2. record expected status, response length, fields, and side effects;
3. change one variable at a time;
4. repeat requests to control for dynamic content;
5. verify server state rather than relying only on text differences.

### Negative testing

High-value negative cases include:

- missing authentication;
- expired or wrong-audience tokens;
- cross-tenant object identifiers;
- duplicated or reordered parameters;
- unexpected HTTP methods;
- malformed content types;
- overlong values;
- missing required fields;
- repeated concurrent requests;
- backend dependency failure.

Automated DAST often misses business logic, workflow abuse, and multi-user authorization testing, so manual analysis remains essential.

## 6. DevSecOps pipeline design

Security checks should provide fast feedback while preserving strong release controls.

### Example pipeline stages

```yaml
stages:
  - validate
  - test
  - security
  - build
  - sign
  - deploy

security:
  steps:
    - run: secret-scan --fail-on-verified-secret
    - run: sast --format sarif
    - run: dependency-scan --lockfile requirements.lock
    - run: iac-scan infrastructure/
    - run: generate-sbom --output sbom.spdx.json
```

This is illustrative rather than tied to a specific CI platform.

### Gate design

A gate should define:

- which finding classes block release;
- how severity is adjusted for reachability and exposure;
- who may approve an exception;
- required compensating controls;
- exception expiration;
- evidence retained;
- how the fix is verified.

If every warning blocks builds, developers may bypass or ignore the system. If nothing blocks, the pipeline becomes informational only. Tuning and ownership matter.

### Protecting the pipeline

The CI/CD system is a production control plane. Controls include:

- MFA and least privilege;
- protected branches and reviews;
- isolated runners;
- short-lived cloud credentials;
- restricted secrets by environment;
- immutable build inputs;
- signed commits or artifacts where appropriate;
- dependency and action pinning;
- audit logs;
- separation between build and deployment approval.

### Software supply-chain controls

- maintain SBOMs;
- verify package provenance;
- use approved registries;
- pin versions and verify hashes;
- monitor maintainership and package changes;
- sign release artifacts;
- protect signing keys;
- rebuild from controlled sources;
- test recovery from a compromised dependency.

## 7. Vulnerability validation and weaponization concepts

Security engineers benefit from understanding how a weakness becomes impact. The objective is not uncontrolled exploitation; it is to validate risk safely.

A validation plan should define:

- authorization and target;
- expected vulnerability preconditions;
- safe proof objective;
- maximum acceptable impact;
- stop conditions;
- evidence to collect;
- cleanup steps;
- detection expectations.

For example, to validate command injection in a lab, the objective might be to cause a harmless, unique marker to appear in server output rather than opening a persistent shell. The proof should demonstrate control of the command context while minimizing side effects.

### Attack-chain reasoning

A low-privileged vulnerability may become critical when chained with:

- exposed credentials;
- weak object authorization;
- writable deployment artifacts;
- cloud instance identity permissions;
- unrestricted outbound network access;
- excessive service-account privileges.

Reporting should explain the chain and the control points that can break it.

## 8. Application logging and evidence

Applications should generate structured events for:

- authentication and account recovery;
- authorization failures;
- role or permission changes;
- administrative actions;
- sensitive data access;
- validation failures indicating attack attempts;
- dependency and queue failures;
- build and deployment changes;
- key and secret operations.

Avoid logging passwords, bearer tokens, session cookies, private keys, or unnecessary personal data. Use correlation identifiers so an API request can be traced through gateway, application, queue, and downstream services.

## 9. Example secure feature review

Feature: users can submit a URL for the application to create a preview.

### Threats

- SSRF to internal services or cloud metadata;
- oversized response causing resource exhaustion;
- redirect to prohibited destination;
- malicious content parser exploit;
- stored XSS in preview metadata;
- DNS rebinding;
- sensitive response content written to logs.

### Controls

- allow only `https`;
- canonicalize URL and validate hostname;
- resolve and reject prohibited IP ranges;
- route through an egress proxy;
- limit redirects and revalidate every destination;
- enforce response size and timeouts;
- parse in a sandboxed non-root worker;
- encode output by context;
- store only required metadata;
- log destination, result, and request ID without sensitive body content.

### Test cases

- loopback and private IP destinations;
- decimal, hexadecimal, IPv6, and alternate hostname representations;
- redirect from allowed to prohibited network;
- slow response and oversized body;
- malformed content;
- concurrent requests;
- output containing script-like content;
- DNS record that changes between validation and fetch.

## Common failure modes

- treating SAST or DAST as complete coverage;
- enforcing authorization only in the UI;
- accepting arbitrary object fields from JSON binding;
- storing long-lived cloud keys in CI;
- scanning dependencies without checking reachability or exposure;
- generating an SBOM but not using it during incidents;
- allowing exceptions without owner or expiry;
- logging sensitive request bodies;
- testing only expected success paths;
- failing to secure the build and signing systems themselves.
