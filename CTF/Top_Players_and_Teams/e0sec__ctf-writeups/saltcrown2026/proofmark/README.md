# Proofmark

| Field | Details |
|-------|---------|
| **Challenge** | Proofmark |
| **Platform** | Cyber Apocalypse CTF 2026: The Salt Crown |
| **Category** | Mobile (Android / Godot) |
| **Flag** | `HTB{p3rf3ct_f4c3_tru3_sp1n3}` |

---

## Overview

> Vaultrune's assay decides which seals are inherited and which were cut from a Signet shard, and every house sends its stamps down to it. Elric Ashspar walks in with a ring he filed himself. If the anvil calls his work inherited, it cannot tell the difference, and neither can anyone else. One strike, no second.

The challenge ships a single `proofmark.apk`: a **Godot 4.7 game** (not a normal Android app) where the player walks around a small forge level, cuts "wards" into a ring at three cutter stations, then presents the ring to an anvil for an "assay". A native **GDExtension** library (`libproofmark.{arm64,x86_64}.so`) performs the actual cryptographic verification; the GDScript layer (`GameState`, `ForgeClient`, `WardCutter`, `Anvil`, `HUD`) is just the game-facing glue.

The flag is generated entirely inside the native library: there is no flag string anywhere in the APK. It has to be computed.

## Unpacking

```bash
unzip mobile_proofmark.zip        # -> proofmark.apk
unzip proofmark.apk -d apk        # standard Android/Godot APK layout
```

Notable contents:

- `lib/{arm64-v8a,x86_64}/libgodot_android.so`: stock Godot engine (huge, ~80MB)
- `lib/{arm64-v8a,x86_64}/libproofmark.{arch}.so`: the **custom GDExtension**, small (~10KB), stripped
- `assets/proofmark.gdextension`: points at the above, entry symbol `proofmark_library_init`
- `assets/scripts/*.gdc`: compiled GDScript bytecode (Godot 4.3+ format: `GDSC` magic + bytecode version + decompressed size + **zstd-compressed** payload)
- `assets/.godot/exported/**/*.scn`: exported/packed scene resources (binary `RSRC` format)

Decompressing a `.gdc` is trivial once you notice the header:

```python
magic, ver, size = data[0:4], u32(data[4:8]), u32(data[8:12])   # b'GDSC', 101, <size>
rest = zstandard_decompress(data[12:])   # raw GDScript tokenizer bytecode
```

Running `strings` over the decompressed bytecode surfaces the game's UI text and variable/function names (`wards`, `bite`, `hallmark`, `file_ward`, `_resync_hallmark`, `reseal`, `submit`, `certificate`, `Proofmark`, `Verdict`, `ACCEPTED`/`REJECT_TOKEN`/`REJECT_STATE`...): enough to sketch the game's logic without a full decompiler:

- `WardCutter` zones each bump one element of `GameState.wards` (a 3-int array) by a fixed `step` when the player walks through.
- `GameState._resync_hallmark()` packs `wards[0..2]` + a `bite` checksum into a 16-byte buffer and calls the native `Proofmark.reseal()`, storing the returned int as `hallmark`.
- At the anvil, `ForgeClient.strike()` calls the native `Proofmark.submit()` with a **fixed 4-int "identity" struct** plus the `hallmark` seed, and reads back a `Verdict` + `certificate` string.

So the real target is `libproofmark.so`.

## Reversing the native library

`libproofmark.x86_64.so` exports exactly one symbol, `proofmark_library_init`, which registers two methods (`reseal`, `submit`) and a `certificate` property via the GDExtension ClassDB API. Both methods forward into two internal, unexported functions found by disassembling with `objdump -d -M intel`.

**`reseal(x, y, z, checksum)`** (`0x1c10`): validates the 4 ints:

```
0 <= x <= 24, 0 <= y <= 24, 0 <= z <= 24
checksum == x + 2*y + 3*z          ; lea ecx,[rcx+2*rdx] ; lea edx,[rsi+2*rsi] ; add edx,ecx
```

then runs those 4 bytes through a small **custom bytecode VM** (a hand-rolled interpreter with an opcode dispatch table, executing an embedded arithmetic "program" that reads bytes out of the input struct) to produce a 32-bit value, which is XORed with `0xa5a5a5a5`, run through two rounds of the MurmurHash3 `fmix32` finalizer, and XORed with `0xbadf00d`. That's the returned "hallmark" seed.

**`submit(magic[4], seed, out_buf, out_len)`** (`0x20d0`): checks that `magic` equals a hardcoded constant embedded in `.rodata` (`83, 67, 55, 462`: the game's fixed "identity" struct, unrelated to the player's wards), then:

1. Runs `state = seed`, then `state = fmix32(state + 0xc2b2ae35)` for exactly **1,200,000 rounds** (a deliberate KDF-style stretch: `mov eax, 0x124f80`).
2. `state2 = state ^ 0x85ebca6b`; `key = fmix32(state2)`.
3. Generates 28 output bytes: each round advances `key` with another `fmix32(key + 0xc2b2ae35)`-style mix, takes the mixed value's **top byte**, XORs it with a fixed 28-byte table from `.rodata`, and writes it to the output buffer.
4. If the first 4 generated bytes equal the literal ASCII `HTB{` (`cmp edx, 0x7b425448`), the buffer is copied out and the verdict is `ACCEPTED`. Otherwise verdict `1` ("assay is cold").

In other words: **the flag is baked into a keystream generator, and only unlocks if the derived seed happens to hash into something starting with `HTB{`.**

## Emulating it precisely

Since the `.so` is a Linux ELF (won't load as a macOS dylib for a real GDExtension), I used **Unicorn** to execute the actual native code directly, mapping the ELF's `PT_LOAD` segments and calling `reseal`/`submit` by address with a tiny System-V ABI shim (and a hand patch for the one `PTEST` instruction Unicorn's TCG doesn't support):

```python
uc.mem_write(0x20e3, b'\xeb\x06' + b'\x90'*5)   # skip PTEST/JE, force success (rdi already matches)
```

I then reimplemented the whole pipeline (`fmix32`, the 1.2M-round stretch, the 28-byte keystream, the XOR table) in pure Python/NumPy and validated it **byte-for-byte** against Unicorn's real execution for multiple seeds before trusting it.

### Dead end #1: brute-forcing the wards

Since `reseal` only accepts `x,y,z ∈ [0,24]` with `checksum = x+2y+3z`, that's only `25³ = 15,625` valid combinations. I ran all of them (and, for good measure, all `25⁴ = 390,625` combinations ignoring the checksum formula) through the full pipeline: vectorized with NumPy so the 1.2M-round stretch runs on all candidates simultaneously, and got **zero** hits. Statistically expected: the target space is 2³², so ~15,625 samples have roughly a 0.3% chance of hitting it at all.

I confirmed via a quick Godot 4.7 headless run of the actual decompiled scene (`WardCutter` nodes `Cutter0/1/2` have `ward_index`/`step` = `(0,6),(1,5),(2,4)`, i.e. wards end up `[6,5,4]`, checksum `28`) that even the game's own intended single-pass wards don't produce the flag. The wards/anvil minigame is flavor: a red herring for "forging a convincing but wrong ring": not the actual path to the flag.

### The real path: invert the hash

`fmix32` is a bijection on 32-bit integers, and every step in `submit()` (the additions, the XOR-shift avalanches, the odd-constant multiplications) is invertible. That means:

- Given the *desired* first 4 output bytes (`HTB{`), I can brute-force the 32-bit **keystream state** entering the 28-byte generator loop directly: only 2³² candidates, and each check is 4 cheap rounds (no 1.2M-round stretch needed), fully vectorizable with NumPy.
- Once found, I don't even need to invert back through the 1.2M rounds to recover the original "seed"/wards: the keystream state alone is enough to run the generator forward for all 28 bytes and read off the certificate.

```python
def modinv(a, m=1<<32): return pow(a, -1, m)
def unxorshift(x, shift):        # invert y = x ^ (x >> shift)
    r = x
    for _ in range(32 // shift + 2):
        r = x ^ (r >> shift)
    return r & 0xffffffff
def fmix32_inv(v):
    v = unxorshift(v, 16); v = (v * modinv(0xc2b2ae35)) & MASK
    v = unxorshift(v, 13); v = (v * modinv(0x85ebca6b)) & MASK
    v = unxorshift(v, 16)
    return v
```

Brute-forcing all `2³²` candidate keystream states for a first-4-byte match (chunked with NumPy, ~256 batches of 2²⁴) found **two** solutions:

```
0x1c7c8990  -> b'HTB{p3rf3ct_f4c3_tru3_sp1n3}'
0x2bd302a4  -> b'HTB{\x03c\xf8\x99y...'   (garbage after the header: false positive)
```

Only the first decodes to a clean, printable, meaningful string: confirming it's the real one, and fitting the challenge's own flavor text (`"PERFECT FACE. WRONG SPINE."`, `"Counterfeits fail where they bear weight."`): the forged ring looks right on the *face* of it, but the deep hash checks the true *spine*.

## Takeaway

A game-side "weak check" (a linear checksum anyone can satisfy) was intentionally there to distract: the real secret was a 1.2M-round KDF-stretched keystream cipher whose output is gated on spelling `HTB{`. Forward brute-force of the (small, game-reachable) input space was hopeless by design; the actual break was recognizing that every primitive used (`fmix32`, modular multiplication by odd constants, XOR-shift avalanches) is a **bijection**, so the target output could be inverted directly instead of searched for from the input side.
