# Atarude

**Category:** Reversing  ·  **Flag:** `ASIS{_iZ_c0p1eD_m4sk5_m4Ke_3Ven_Spl!c3s_vAn1sh!!?}`

## Challenge Description

A stripped, statically-linked Rust binary (`Atarude`, ~13 MB: provided binary, not included
due to size) plus `flag.enc` (70 bytes). Running the program only shows a `>` prompt; bad input
replies with a terse `no`. The program exposes six independent "lanes," each of which will
encrypt two fixed messages and asks us to submit a third, fresh, valid ciphertext per lane.
Solving all six lanes decrypts `flag.enc`.

## Initial Analysis

Reversing the input parser reveals two commands:

```text
e <lane> <hex plaintext>   # ask the encryption oracle (decodes to 160 bytes = 10 blocks)
s <lane> <hex ciphertext>  # submit a forged ciphertext (decodes to 176 bytes = 11 blocks)
```

Rules discovered from the binary:

1. Each lane allows exactly two successful `e` queries.
2. The oracle refuses arbitrary plaintext: each query must equal a hidden 160-byte value
   generated by the binary.
3. A submitted ciphertext must differ from both oracle ciphertexts.
4. All six lanes must pass before the flag is decrypted.

The hidden oracle inputs are recovered in a debugger. For a PIE, break after computing the
load base, stop just before the 160-byte comparison completes, and dump the expected bytes
from the stack (in this build, at `$rsp + 0xd0`, comparison near VA `0xc29ced`):

```gdb
starti
set $base = $pc - 0xc24170
b *($base + 0xc29bf0)
continue
dump binary memory expected.bin $rsp+0xd0 $rsp+0x170
```

Temporarily patching the final equality branch (`je` → `jmp; nop`) lets a dummy input reach
the success path so both messages per lane can be dumped. This patch is only a reversing aid: the final exploit runs against the unmodified binary.

## Vulnerability / Core Concept

**Structural weakness in the ciphertext verifier.** For each lane the two required oracle
messages have the form `A || T` and `B || T`: only the first of ten plaintext blocks differs,
the 144-byte tail `T` is identical. (These constants live in the `FIRST` / `TAIL` arrays in
`solve.py`.)

After the custom AES/GF(2^128)-style decode of a submitted 176-byte ciphertext, the acceptance
test is tiny:

```asm
movdqu  xmm0, [rsp+0x170]
pcmpeqb xmm0, xmm1        ; xmm1 = 0
pmovmskb eax, xmm0
xor     eax, 0xffff
je      accepted          ; accept iff the FIRST decoded 16-byte block is all zero
```

Only the first decoded block must be zero: the other ten may be anything. Treating the
176-byte ciphertext as eleven 16-byte blocks, we can **splice** blocks from the two known
oracle ciphertexts. There are only 2^11 = 2048 masks (2046 non-trivial), so we enumerate them,
break right after the decoder, and keep masks whose first decoded block is zero.

Each lane yields a complementary pair of masks. Both pass the local check, but after all six
lanes are solved the binary hashes the 66 submitted blocks (domain `0x5f`) against a built-in
digest: this final aggregate check selects one specific orientation per lane.

## Exploitation

The working masks (blocks taken from `C1`, all others from `C0`):

| Lane | Mask   | Blocks from C1 |
|-----:|:-------|:---------------|
| 0 | `0x0e0` | 5, 6, 7 |
| 1 | `0x1a0` | 5, 7, 8 |
| 2 | `0x2c0` | 6, 7, 9 |
| 3 | `0x360` | 5, 6, 8, 9 |
| 4 | `0x2a0` | 5, 7, 9 |
| 5 | `0x340` | 6, 8, 9 |

`solve.py` drives the binary directly: it replays the two recovered messages per lane, splices
the resulting ciphertexts with the lane mask, and submits the forgery.

```bash
$ ./solve.py ./Atarude
ok
ok
ok
ok
ok
ASIS{_iZ_c0p1eD_m4sk5_m4Ke_3Ven_Spl!c3s_vAn1sh!!?}
```

## Flag

## Key Takeaways

- A giant Rust binary with scary custom crypto can hide a trivially weak verifier: here the
  check only inspects one output block.
- Recover the exact oracle inputs from the stack rather than trying to reverse the generator.
- Wide-block ciphertext splicing is cryptographic cut-and-paste: enumerate 2^11 block masks
  when the acceptance condition is that local.
- A separate aggregate digest over all lanes disambiguates complementary solutions.
