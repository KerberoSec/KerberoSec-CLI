# Module 6: OWASP Top 10 (2025)

> **Portfolio scope:** Technical analysis of the OWASP Top 10:2025 categories as grouped in the TryHackMe module: IAAA failures, application design flaws, and insecure data handling. This is not an answer dump or a reproduction of room tasks.

## Module coverage

The OWASP Top 10:2025 contains:

1. A01: Broken Access Control
2. A02: Security Misconfiguration
3. A03: Software Supply Chain Failures
4. A04: Cryptographic Failures
5. A05: Injection
6. A06: Insecure Design
7. A07: Authentication Failures
8. A08: Software or Data Integrity Failures
9. A09: Security Logging and Alerting Failures
10. A10: Mishandling of Exceptional Conditions

TryHackMe grouped these into three practical themes:

- **IAAA failures:** A01, A07, A09;
- **application design flaws:** A02, A03, A06, A10;
- **insecure data handling:** A04, A05, A08.

The categories overlap. A single attack chain may involve weak authentication, broken object authorization, injection, and inadequate logging.

# Part I: IAAA failures

IAAA stands for identity, authentication, authorization, and accountability.

## A01: Broken Access Control

### Technical cause

Broken access control occurs when the server fails to enforce what an identity may do. Common forms include:

- IDOR or broken object-level authorization;
- missing function-level authorization;
- privilege escalation through role or claim tampering;
- forced browsing to hidden endpoints;
- CORS or cross-origin policy mistakes that expose sensitive functions;
- server-side request forgery included in the 2025 category;
- path traversal and unauthorized file access;
- authorization performed only in client-side code;
- default-allow policy or inconsistent checks between services.

### Test methodology

1. map users, roles, objects, and functions;
2. obtain at least two lab identities with different ownership or privileges;
3. capture a valid request;
4. change object IDs, tenant IDs, role claims, methods, and endpoints one at a time;
5. test direct API access without the UI;
6. test nested objects and bulk operations;
7. verify denied attempts are logged;
8. inspect side effects, not only response text.

Example object-level test:

```http
GET /api/invoices/1001
Authorization: Bearer <user-A-token>
```

Change only `1001` to an invoice owned by user B. A secure system checks ownership or policy on the server for every request.

### Remediation

- centralize authorization policy;
- default deny;
- enforce object- and function-level checks server-side;
- use indirect identifiers only as defense in depth, not as the primary control;
- isolate tenants in data access patterns;
- add negative authorization tests;
- protect internal outbound requests with URL and egress policy;
- log failures with actor, target, action, and request ID.

## A07: Authentication Failures

### Technical cause

Authentication failures allow an attacker to impersonate a user or maintain an unauthorized session. Examples include:

- weak or default credentials;
- credential stuffing without rate controls;
- unsafe password reset;
- MFA bypass or weak fallback;
- predictable or reusable session identifiers;
- session fixation;
- failure to revoke sessions after password reset or account disablement;
- tokens accepted with wrong issuer, audience, algorithm, or expiry;
- long-lived bearer tokens exposed to lower-trust clients;
- user enumeration through messages or timing.

### Token validation checklist

For JWT-like tokens, the verifier should:

- allow only expected algorithms;
- validate signature with the correct key;
- verify issuer and audience;
- enforce expiry and not-before claims;
- validate token type and scope;
- reject unsigned or malformed tokens;
- rotate keys safely;
- prevent key-confusion or untrusted key URL behavior;
- support revocation or short lifetimes where risk requires.

### Session controls

- use `Secure`, `HttpOnly`, and appropriate `SameSite` cookie attributes;
- rotate session IDs after authentication and privilege change;
- expire inactive and absolute sessions;
- revoke on logout, password reset, and account disablement;
- bind sensitive actions to recent authentication;
- protect account recovery more strongly than normal login.

### Remediation

- phishing-resistant MFA for privileged access;
- password screening and secure KDF storage;
- rate limiting and anomaly detection;
- secure recovery with identity verification;
- generic error messages;
- short-lived, scoped tokens;
- device and risk context;
- comprehensive authentication telemetry.

## A09: Security Logging and Alerting Failures

### Technical cause

Security events may be absent, incomplete, unprotected, or ignored. Failure includes:

- no logging for authentication or authorization failures;
- missing administrator and data-access events;
- insufficient context to identify the actor or target;
- logs stored only on the compromised host;
- no alerting or response owner;
- excessive sensitive data in logs;
- log injection through unencoded input;
- time drift;
- short retention;
- silent ingestion failure.

### Minimum event fields

- UTC timestamp;
- actor and session;
- source IP/device;
- action;
- target resource;
- result;
- request/correlation ID;
- application and environment;
- relevant policy or authorization decision.

### Detection examples

- repeated cross-object access denials;
- many failed logins followed by success;
- new MFA method registration;
- privileged role assignment;
- logging configuration change;
- audit-log deletion;
- bulk export or unusual record access;
- high-volume application exceptions.

### Remediation

- define a logging standard;
- centralize and protect logs;
- monitor pipeline health;
- design actionable alerts with owners and runbooks;
- test detections through controlled simulations;
- redact credentials and sensitive content;
- retain enough context for investigation.

# Part II: Application design flaws

## A02: Security Misconfiguration

### Technical cause

Misconfiguration includes insecure defaults, unnecessary features, weak headers, exposed management interfaces, excessive cloud permissions, public storage, verbose errors, missing hardening, and inconsistent environments.

### Assessment workflow

- enumerate services and interfaces;
- compare against an approved baseline;
- inspect HTTP security headers and cookies;
- review debug and error behavior;
- check default accounts and sample content;
- review cloud public-access and IAM configuration;
- inspect container runtime privileges;
- verify environment separation;
- test whether configuration changes are detected.

### Remediation

- infrastructure as code and reviewed templates;
- hardened defaults;
- remove unused services and packages;
- automated configuration scanning;
- policy as code;
- separate secrets from configuration;
- minimize privilege;
- standardize error responses;
- detect drift continuously.

---

## A03: Software Supply Chain Failures

### Technical cause

The application depends on code, packages, build systems, registries, CI actions, container images, and signing infrastructure. A compromise anywhere in this chain can alter what reaches production.

Threats include:

- malicious or hijacked dependency;
- dependency confusion;
- typosquatting;
- compromised maintainer account;
- unpinned CI action;
- poisoned build runner;
- exposed package-registry credential;
- unsigned artifact replacement;
- vulnerable or abandoned dependency;
- tampered base image.

### Controls

- approved package sources;
- lockfiles and hash verification;
- dependency review and SCA;
- SBOM generation;
- isolated, ephemeral build runners;
- short-lived deployment credentials;
- protected branches and reviews;
- artifact signing and provenance;
- image signing and admission policy;
- rapid identification of affected products during incidents.

### Validation

- attempt a build with an unapproved registry;
- confirm unsigned artifacts are rejected;
- inspect whether CI actions are pinned to immutable versions;
- verify build credentials cannot access unrelated environments;
- trace a deployed artifact back to source commit, build, and signer.

## A06: Insecure Design

### Technical cause

Insecure design exists when the architecture lacks necessary controls, even if the implementation is bug-free. Examples:

- unlimited password-reset attempts;
- no separation between user and administrator workflows;
- approval process that can be completed by the requester;
- business rule enforced only by the client;
- no tenant-isolation strategy;
- unsafe trust in internal networks;
- absence of abuse-case handling;
- sensitive process with no replay or concurrency protection.

### Design controls

- threat modelling;
- misuse and abuse cases;
- secure reference architectures;
- least privilege and separation of duties;
- state-machine and workflow validation;
- quotas and anti-automation controls;
- explicit trust boundaries;
- secure failure modes;
- security requirements tied to tests.

### Example: coupon redemption

A code-level patch cannot fix a design that allows concurrent redemption without an atomic transaction. The system needs a state transition enforced by the database or transaction service so only one redemption can succeed.

## A10: Mishandling of Exceptional Conditions

### Technical cause

This 2025 category covers failure to prevent, detect, or respond safely to abnormal conditions. Examples include:

- failing open when a dependency is unavailable;
- exposing stack traces and sensitive internals;
- swallowing authorization or transaction errors;
- resource leaks after exceptions;
- incomplete rollback;
- inconsistent error handling;
- race conditions and partial state;
- missing parameter handling;
- null dereference or unbounded retry loops;
- insecure fallback behavior.

### Secure error-handling principles

- validate early and close to the source;
- handle errors at the appropriate layer;
- fail closed for authorization and sensitive operations;
- use bounded retries with backoff;
- release resources in all paths;
- avoid exposing internal details;
- generate correlation IDs;
- roll back partial transactions;
- test dependency failure, timeout, and malformed input;
- alert on repeated exceptional conditions.

### Example failure path

A payment service requests a fraud decision. If the fraud service times out, approving the payment by default is a fail-open design. Safer behavior may be to decline, queue for manual review, or apply a restricted fallback based on business risk.

# Part III: Insecure data handling

## A04: Cryptographic Failures

### Technical cause

- sensitive data transmitted without TLS;
- weak or obsolete algorithms;
- hard-coded keys;
- nonce/IV reuse;
- encryption without integrity;
- passwords stored with fast hashes;
- invalid certificate handling;
- keys stored with the protected data under identical access;
- missing rotation and revocation;
- sensitive data collected unnecessarily.

### Assessment

- identify sensitive data and lifecycle;
- inspect protocols and certificate validation;
- review algorithms, modes, and key sizes;
- trace key storage and access;
- review password-storage parameters;
- inspect logs, backups, exports, and temporary files;
- test expired or invalid certificates in non-production environments.

### Remediation

- use modern authenticated encryption;
- use approved TLS configurations;
- use dedicated password KDFs;
- manage keys through a controlled service;
- rotate and audit key use;
- minimize data collection;
- separate keys by environment and purpose;
- remove secrets from source and artifacts.

## A05: Injection

### Technical cause

Injection occurs when untrusted data is interpreted as code, syntax, or control input by a downstream system.

Common sinks:

- SQL and NoSQL queries;
- shell commands;
- LDAP and XPath;
- template engines;
- email headers;
- log processors;
- HTML/JavaScript output, including XSS;
- expression languages.

### Testing model

Trace **source → transformations → sink**. Determine:

- whether user input reaches the sink;
- whether parameterization or context-specific encoding is used;
- whether authorization limits impact;
- whether errors, timing, or side effects confirm interpretation;
- whether alternate encodings bypass normalization.

### Remediation

- parameterized APIs;
- avoid shell execution;
- allow-list structured input;
- context-aware output encoding;
- safe template modes;
- least-privileged service accounts;
- sandbox risky parsers;
- negative tests and code review.

Input “sanitization” alone is often fragile because the correct defense depends on the sink.

## A08: Software or Data Integrity Failures

### Technical cause

Systems may trust code, updates, serialized data, or workflow state without verifying integrity. Examples:

- unsigned updates;
- insecure deserialization;
- untrusted CI/CD artifacts;
- client-controlled state accepted by the server;
- webhook messages without signature validation;
- race conditions causing inconsistent transactions;
- package or image tampering;
- backups restored without integrity verification.

### Controls

- digital signatures and provenance;
- strict deserialization formats;
- avoid native object deserialization from untrusted data;
- webhook signatures with timestamp/replay protection;
- server-side state and authorization;
- atomic transactions and concurrency control;
- artifact and image admission policies;
- immutable logs and protected backups.

### Webhook validation example

A webhook receiver should:

1. read the raw request body;
2. verify the provider’s signature with the correct secret/key;
3. validate timestamp and allowed clock skew;
4. reject replayed event IDs;
5. validate schema and event type;
6. authorize the affected tenant/resource;
7. process idempotently;
8. log result and correlation ID.

# Integrated test scenario

Application: multi-tenant note-sharing service.

### Possible findings

- A01: changing `noteId` accesses another tenant’s note;
- A07: password reset token remains valid after use;
- A09: cross-tenant attempts are not logged;
- A02: debug endpoint exposes environment variables;
- A03: build uses unpinned third-party CI action;
- A06: shared-note workflow has no owner approval for public publication;
- A10: authorization service timeout causes the application to allow access;
- A04: notes use one shared encryption key stored in the same database;
- A05: search parameter reaches a SQL query through string concatenation;
- A08: import feature deserializes an untrusted native object.

### Priority reasoning

The findings should be prioritized by exploitability, exposure, data sensitivity, control coverage, and chaining potential. Broken tenant isolation combined with weak logging may deserve immediate action even if several lower-impact misconfigurations also exist.

## Common failure modes

- using the OWASP Top 10 as a complete security standard;
- testing categories independently and missing attack chains;
- treating authentication as proof of authorization;
- relying on hidden buttons or unguessable IDs;
- focusing only on input validation while ignoring workflow design;
- encrypting data but exposing keys through the same identity;
- generating logs that no one monitors;
- returning verbose stack traces;
- trusting build outputs without provenance;
- allowing sensitive operations to fail open.

---

## Portfolio takeaway

I learned to use the OWASP Top 10 as an awareness and testing framework, not a substitute for threat modelling or ASVS-level requirements. The strongest analysis follows identities, objects, data, code, and failure paths across the complete system and verifies both prevention and detection.
