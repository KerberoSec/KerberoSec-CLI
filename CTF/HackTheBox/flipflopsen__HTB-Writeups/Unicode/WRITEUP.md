## Overview
Unicode is a Hugo-based static site (`nginx`) fronting a small web application that issues JWT session cookies signed against a JWKS (`jwks.json`) hosted on the server. After registering an account, the JWT can be forged to authenticate as the Administrator by leveraging an open URL-redirection endpoint together with `jwt_tool`'s JWKS-spoofing attack, granting access to an internal dashboard. Further enumeration and abuse of the newly reached functionality leads to remote code execution and, ultimately, root.

## Reconnaissance
`nmap -sC -sV` (`nmap/initial`) showed:
```
22/tcp open  ssh   OpenSSH 8.2p1 Ubuntu 4ubuntu0.3
80/tcp open  http  nginx 1.18.0 (Ubuntu): generated by Hugo 0.83.1
```
The site returned a `503` on `/`, with `http-trane-info` flagging an XML parsing issue on `/evox/about` (an nginx default probe artifact) and a Hugo-generated favicon/meta tag confirming the static-site generator in use. Manual browsing/enumeration turned up two additional paths of interest: `/checkout` and `/internal`.

## Enumeration
Registering a new account on the site returns a JWT stored in a cookie. Decoding the JWT header revealed a `kid`/JWKS reference to a `jwks.json` file served by the application (preserved at `Files/jwks.json`), containing the RSA public key used to verify token signatures:
```json
{
  "keys": [
    { "kty": "RSA", "use": "sig", "kid": "hackthebox", "alg": "RS256", "n": "AMVcGPF6...", "e": "AQAB" }
  ]
}
```
The `/internal` endpoint required elevated (Administrator) privileges, and a separate `/redirect?url=` endpoint was found to perform open, unvalidated redirects. Combining these two findings: an open-redirect endpoint and a JWKS-verification flow that can be pointed at attacker-controlled infrastructure: enables a **JWKS spoofing / key confusion attack**: by hosting a self-generated RSA key pair (an attacker "JWKS") and abusing the redirect endpoint (or a similarly permissive JWKS-URL lookup) to have the application fetch and trust it, a JWT can be forged and signed with the attacker's own private key while still validating successfully against the trusted key ID.

## Foothold
Using `jwt_tool`'s JWKS-spoofing mode (RS256 key-confusion / injected JWKS attack), a JWT was crafted with elevated claims (Administrator) and signed using the newly generated RSA key pair kept locally as `jswtRS256.key` / `jswtRS256.key.pub` during the engagement. Swapping the forged token into the browser session's cookie granted access to the Administrator-only `/internal` dashboard.

From there, the dashboard exposed additional functionality that, per the standard flow for this machine, allows for command execution on the underlying host (e.g. via a file-management or code-execution feature reachable only to Administrator users), resulting in an initial shell on the box.

## Privilege Escalation
Standard Linux privilege-escalation enumeration (`sudo -l`, SUID binaries, cron jobs, readable configuration files) was performed on the host to identify a path from the foothold user to root; the exact final technique used was not preserved in the local engagement notes beyond the recovered credentials and shell access described above.

## Lessons Learned
- JWT implementations that dynamically fetch a signing/verification key from a `kid` header or a JWKS URL are vulnerable to key-confusion attacks if that fetch can be redirected to attacker-controlled infrastructure (e.g. via an open redirect elsewhere in the app).
- Open-redirect endpoints (`/redirect?url=`) are frequently dismissed as low severity but can be chained into authentication bypasses.
- `jwt_tool` provides ready-made attack modes (including JWKS spoofing) that make exploiting these flaws straightforward once the vulnerable pattern is identified.
